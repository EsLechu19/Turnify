# PROMPT — Arquitectura y stack del proyecto Turnify (detalle minucioso)

> Pega todo lo de abajo como contexto para explicar, documentar o presentar la arquitectura y el stack de Turnify. No inventes versiones ni componentes: usa solo lo declarado aquí.

## 1. Qué es Turnify

Plataforma de gestión de colas para barberías con tres superficies: (a) app móvil Android para clientes invitados (sin cuenta) y trabajadores (barberos/personal); (b) panel web SPA para administradores; (c) backend Supabase (PostgreSQL + Auth + Realtime + Storage + Edge Functions + cron). El dominio central es el ticket con máquina de estados: `en_espera → notificado → llamado → en_atencion → finalizado / ausente / cancelado`. Regla de oro: el cliente jamás escribe tablas directamente; toda mutación pasa por funciones RPC `SECURITY DEFINER` con `search_path = ''`, y el acceso se gobierna con Row Level Security por rol (`cliente`, `personal`, `admin`).

## 2. Monorepo y layout

- `apps/mobile/` — Expo SDK 57, React Native 0.86.3, React 19.2.3, `expo-router` con rutas por archivos (`app/index.tsx` público, `app/(public)/` flujo invitado: `scan|shop|service|barber|details|ticket`, `app/(auth)/login|register`, `app/(app)/` cliente y trabajador: `worker|worker-queue|worker-walk-in|worker-history|worker-profile|worker-services|worker-shops|worker-account-profile|profile|barbers|history`). TypeScript estricto (`tsc --noEmit`), `typedRoutes` y React Compiler activados en `app.json`.
- `apps/web/` — React 19 + React Router (`/` Inicio, `/servicios`, `/equipo`, `/historial`, `/configuracion`, `/cuenta`, `/login`, `/register`), Recharts para gráficos, Supabase JS, Vitest.
- `packages/types/` — tipos compartidos (`database.ts` incluye firma de `crear_empresa`).
- `supabase/migrations/` — 55 migraciones versionadas (`0001`–`0055`): esquema base, RPCs de cola, invitaciones de personal, membresías multi-local, catálogo comercial, push de llamados, fotos, walk-ins, cuenta admin y fixes (`0045` catálogo perfil, `0046` push invitado, `0047/0048` foto admin, `0049–0051` ticket manual, `0052` espera con ritmo medido, `0053–0055` invitaciones).
- `supabase/functions/dispatch-ticket-calls/` — Edge Function Deno: reclama entregas `pendiente` del outbox, envía vía Expo Push API (`https://exp.host/--/api/v2/push/send`), exige receipt `ok`, marca `entregada` o `indeterminada` (sin reintentos ciegos para no duplicar), purga dispositivos invitados expirados. Autorización solo con token dedicado de cron comparado en tiempo constante; JWT del gateway desactivado solo para ella.
- `tests/` — suites Vitest por dominio (`tests/mobile`, `tests/web`, `tests/supabase`, `tests/notifications`): 360+ pruebas de contrato que leen fuentes y migraciones.
- `docs/` — informe del proyecto, HU (`HU_Turnify.md`, 56 historias), este prompt.
- `scripts/live-validation/` — validación contra backend vivo (`crear_empresa`, etc.).

## 3. Móvil: dependencias y piezas clave

Dependencias nativas: `expo-camera` (scanner QR con permiso declarado), `expo-notifications` (push, solo builds de desarrollo/producción, nunca Expo Go; tras kill-switch `EXPO_PUBLIC_ENABLE_PUSH=1`), `expo-haptics` (vibración al escanear/llamar/confirmar/votar), `expo-location` (distancia/ETA), `expo-secure-store` (sesión), `expo-dev-client`, `react-native-svg`, `react-native-reanimated`, `react-native-qrcode-svg`, `react-native-gesture-handler/safe-area-context/screens`. UI propia sin framework externo: `components/ui` (`Button` con 9 variantes, ripple Android nativo, dots de carga, press 0.985; `OptionCard/Row`, `Card`, `Pill`, `Skeleton` con pulso 1200ms, `Mascot` oveja con respiración 2.2s y modo `celebrate`, transiciones nativas por flujo: slide 280ms público, fade 200ms tabs, fade 220ms auth). Estado: contextos `AuthContext` (sesión/perfil/rol), `GuestFlowProvider` (capability SOLO en memoria React —prohibido serializarla en rutas o storage, verificado por tests), colas por RPC. Tiempo real: canales Realtime por ticket/empresa + re-sincronía al volver a primer plano + polling de 10s solo con llamado activo. Push invitado: token Expo atado a (ticket, hash de capability) vía `registrar_dispositivo_invitado`, expira en 1 día, se revoca al terminar; el tap rutea al ticket en llamado. Haptics + `LayoutAnimation` en cola del trabajador; `AccessibilityInfo.isReduceMotionEnabled` respeta movimiento reducido. Build: EAS perfil `production` (`buildType: apk`, `autoIncrement`, `appVersionSource: remote`), paquete `com.esau01s.turnify`, sin permiso de micrófono, cámara/ubicación con textos de permiso en español.

## 4. Web: piezas clave

Estado por contextos (`AuthContext` con `signUp` y `refreshProfile`, `ShopContext` con `open` vivo + `refreshShop`, `QueueContext` con snapshot + `refreshVersion` y polling 15s + foco, `ServicesContext`). Inicio: veredicto operativo con siguiente código y acciones, stats sin duplicar con tendencias semánticas (subir ausentes/espera = mal), alertas con botón a destino (`/equipo|/historial`), cola viva de lectura, ingresos estimados (finalizados × precios de referencia, etiquetado estimado). Servicios con CRUD, asignación por barbero y `ref.` explícito. Equipo con invitación nominativa (código 7 días), aprobación/denegación con confirmación, bloqueo de edición en atención, columna turno actual. Historial con filtros, gráficos propios, CSV e impresión. Configuración con abrir/cerrar instantáneo, renombre con refresh vivo, QR, tolerancias, ubicación Nominatim y descarte confirmado. Mi cuenta (foto vía RPC espejo del worker, nombre, clave) y auto-registro (`/register`: cuenta + local + código de mostrador). Marco sin duplicados: campana viva con conteo, identidad de sesión, un solo logout. Auth: solo `admin` opera (barbero rebotado con mensaje neutro a login).

## 5. Datos y seguridad

Tablas núcleo: `empresas` (código único de 8), `filas`, `tickets` (snapshot de servicio/nombre, `fecha_operativa` Lima, `acceso_publico_hash` SHA-256, `origen` app/presencial), `servicios` (estimado + medido trimmed-mean últimos 30), `barberos` + `barbero_servicios` (asignación = capacidad real), `barbero_operaciones` (disponible/ocupado/fuera), `membresias_personal_empresa` (multi-local con actual seleccionada server-side), `perfiles` (rol, foto global), `solicitudes_invitacion_personal` (hashes, expiración, anti-duplicado por índice único parcial), `dispositivos` (por `auth.uid`, único global) y `dispositivos_invitados` (por ticket, expirable), outbox `notificaciones_salientes` + `notificacion_entregas` (claim at-most-once, `sin_destinatarios` sin receptores). RPCs representativos: `crear_ticket_invitado`, `tomar_turno_comercial`, `catalogo_comercial`, `mi_cola_barbero` (filtra por compatibilidad + manuales del creador con `origen='presencial'`), `llamar_mi_siguiente` (compatibles primero, manuales después), `crear_mi_ticket_presencial` (servicio y barbero opcionales validados), `crear_empresa` (crea local + cola General + promueve a admin), invitación nominativa completa, `actualizar_mi_foto_barbero/admin`, `registrar/revocar_dispositivo[_invitado]`. Estimación de espera: ritmo medido (promedio últimas 10 finalizadas a 30 días) con fallback a snapshot; cliente muestra posición como hecho y tiempo solo como `~` aproximado, jamás “0 min” falso. Variables: `EXPO_PUBLIC_SUPABASE_URL/ANON_KEY/ROUTING_PROVIDER/OPENROUTESERVICE_KEY/ENABLE_PUSH`; secretos de servidor (`SERVICE_ROLE`, `EXPO_ACCESS_TOKEN`, cron token) solo en Vault/entorno, nunca en fuente.
